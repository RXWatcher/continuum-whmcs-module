# Free Silo Rollout Design

## Goal

Provision one immediately active Silo service for each WHMCS client who has an
active Emby service. The new Silo service is free during the pre-launch period,
sends no client email, and does not modify or replace the existing Emby service.

## Confirmed Live Configuration

- WHMCS installation: `/opt/whmcs` on `wave-ninja`
- Source Emby product group: ID `9` (`E Hosting Services`)
- Target Silo product: ID `122`
- Target Silo server: ID `123` (`Silo (lib.strm.cafe)`)
- Current target product name: `S - 3 Concurrent`
- New target product name: `S - Service`
- Target product module: `silo`
- Target product automatic setup: enabled when the order is placed
- Target product welcome email: disabled
- Existing active Silo services on product 122: 2
- Observed eligible clients before execution: 118

The observed count is informational. The execution-time dry run is authoritative
because service state can change between design approval and execution.

## Eligibility

A client is eligible when all of the following are true at execution time:

1. The client has at least one WHMCS service whose product belongs to group 9.
2. At least one such Emby service has `domainstatus = Active`.
3. The client has no WHMCS service, in any status, whose product belongs to the
   Silo product group (group 15).

Clients are deduplicated by WHMCS client ID. Multiple active Emby services still
produce only one Silo service. Existing Silo services are never altered.

## Product Change

Product 122 is renamed to `S - Service`. This intentionally changes the display
name for its two existing services as well as the newly created services. Its
configured recurring prices, tax setting, module, server, automatic setup, and
all other product settings remain unchanged.

Each rollout service receives service-level billing values of:

- Billing cycle: `Free`
- First payment amount: `0.00`
- Recurring amount: `0.00`
- Invoice generation: disabled for the creation operation

The normal product pricing remains available for the later paid migration.

## Execution Tool

Use a temporary CLI-only PHP rollout command outside the web root. It loads the
WHMCS runtime, queries through Capsule, and creates services through the WHMCS
local API. It supports three explicit modes:

- `--dry-run`: default; makes no changes and prints aggregate counts plus client
  IDs only.
- `--execute-canary`: performs the approved rename and provisions exactly one
  eligible client, then stops for verification.
- `--execute-all`: provisions the remaining eligible clients only after the
  canary has been recorded as verified.

The command uses a process lock to prevent concurrent runs. It writes a
timestamped JSON Lines audit file under `/root` with restrictive permissions.
Each record contains the client ID, order ID, service ID, prior eligibility
check, WHMCS API results, provisioning result, and error text. It does not log
passwords, API credentials, names, or email addresses.

## Provisioning Flow

For each candidate, the command performs the following steps independently:

1. Recheck eligibility immediately before creation.
2. Use WHMCS `AddOrder` for product 122 with a free billing cycle, a zero price
   override, no invoice, and `noemail` enabled.
3. Inspect the resulting service before taking another provisioning action.
4. If automatic setup has already activated the service, record success.
5. If the service remains pending, accept the order with automatic setup enabled
   and order email disabled.
6. Confirm that the service is assigned to server 123, has product 122, is
   `Active`, and has zero first and recurring amounts.
7. Record the result before moving to the next client.

The first eligible client is a canary. `--execute-canary` stops after that client
so the service, Silo account, module log, WHMCS email log, and mail queue can be
checked. The operator records the successful check in the audit state. The
`--execute-all` mode refuses to run without that verified-canary state.

The audit log makes the run resumable. A resumed run recomputes eligibility and
therefore skips the canary and every other client who now has a Silo service.

## Email Suppression

No global WHMCS or Postfix mail setting is changed. This avoids suppressing
unrelated production mail while the rollout runs.

The rollout suppresses all standard messages generated by its own workflow:

- `AddOrder` is called with `noemail` enabled.
- Invoice generation is disabled for these free orders.
- Order acceptance is called with its send-email option disabled.
- Product 122 has no welcome email template assigned.
- The Silo provisioning module contains no email-sending operation.

Before the canary, capture the WHMCS email-log high-water mark and Postfix queue
state. After the canary and after the full run, verify that no email-log row was
created for a rollout client and that the operation did not add queued mail.

## Failure Handling

Processing is serial so each result is known before the next client begins. A
client failure does not stop unrelated clients after the canary stage, but it is
recorded and included in the final failure count.

The command never retries a failed module action automatically. Before a manual
retry, the operator must inspect both WHMCS and Silo for a partially created or
linked account. This avoids duplicate external accounts when WHMCS receives an
ambiguous response.

If an order exists but provisioning fails, the service is left visible in its
actual WHMCS state for diagnosis. It is not silently deleted.

## Verification

The rollout is complete only when all of these checks pass:

- Product 122 is named `S - Service` and its other settings are unchanged.
- Every client in the dry-run candidate set who remained source-eligible through
  execution has exactly one Silo-group service.
- Every newly created service uses product 122 and server 123.
- Every successful new service is `Active`, uses billing cycle `Free`, and has
  first and recurring amounts of `0.00`.
- Existing Emby services have unchanged status, product, pricing, and server.
- The number of successful services plus recorded failures equals the dry-run
  candidate count, adjusted only for eligibility changes recorded during the run.
- No rollout client email was added to the WHMCS email log.
- No rollout-generated message was added to the Postfix queue.

## Rollback

The product rename can be reversed independently by restoring the captured
pre-run product name. Successful Silo services are not automatically rolled back
when another client fails.

A full rollback uses only service IDs from the rollout audit file. For each ID,
the operator first invokes the Silo termination action and verifies the external
account outcome, then cancels or removes the corresponding WHMCS service and
order. No pre-existing Silo service is included. Because termination can delete
or retain external accounts according to product configuration, a full rollback
requires a separate explicit approval after those settings are rechecked.

## Out of Scope

- Changing, suspending, terminating, or repricing any Emby service
- Switching client access from Emby to Silo
- Charging for the new Silo services
- Changing product 122's normal configured prices
- Sending migration announcements or credentials
- Automatically deleting failed or partially provisioned services
